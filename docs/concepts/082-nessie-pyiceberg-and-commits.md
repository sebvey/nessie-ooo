How commits work with Nessie, the Iceberg REST API, and PyIceberg

This document explains factually and step by step how commits are created and managed when you use:
	•	Nessie as a versioned catalog
	•	Iceberg REST API as the catalog protocol
	•	PyIceberg as the Iceberg engine

The goal is to clearly separate what Nessie does, what the REST API allows, and what PyIceberg actually implements today.

⸻

1. What a “commit” means in Nessie

In Nessie, a commit is a catalog-level concept.

A Nessie commit records:
	•	a change in catalog state
	•	on a specific branch
	•	with a commit hash

Concretely, a commit captures:
	•	which tables exist
	•	which metadata file each table points to

A commit does not store table data, and does not store Iceberg snapshots themselves.

Think of a Nessie commit as:

“At this moment, the catalog points to these table metadata locations.”

⸻

2. Branches and tags in Nessie (quick reminder)
	•	Branch: a mutable pointer to a commit
	•	Tag: an immutable pointer to a commit

Commits form a graph, just like Git:

main ──●──●──●
         \
          ──●──●  dev


⸻

3. What the Iceberg REST API is (and is not)

The Iceberg REST catalog API is:
	•	a generic, engine-agnostic protocol
	•	designed so engines (Spark, Flink, PyIceberg, etc.) can talk to catalogs

Important constraints of the REST API:
	•	it defines table metadata operations, not user workflows
	•	it does not require engines to expose commit messages or authors
	•	it allows, but does not mandate, commit metadata

The REST API’s job is:

“Apply this table metadata update atomically.”

⸻

4. How Nessie implements the Iceberg REST catalog

When Nessie acts as an Iceberg REST catalog:
	•	it receives REST requests from an engine
	•	it wraps table-metadata updates into Nessie commits
	•	each successful table update results in one Nessie commit

Crucially:

Nessie maps one catalog commit to one Iceberg snapshot.

This mapping is intentional and enforces consistency.

⸻

5. What PyIceberg does when it “commits”

From PyIceberg’s point of view, there is no Nessie commit object.

PyIceberg performs the following steps:
	1.	Load table metadata via the REST catalog
	2.	Apply an Iceberg operation (append, overwrite, etc.)
	3.	Produce:
	•	a new Iceberg snapshot
	•	a new metadata JSON file
	4.	Send a REST request to the catalog:
	•	“replace table metadata with this new metadata file”

That’s it.

PyIceberg:
	•	does not name commits
	•	does not assign messages
	•	does not manage branches or tags

It simply asks the catalog to atomically apply the update.

⸻

6. How a Nessie commit is created during a PyIceberg write

When Nessie receives the REST request from PyIceberg:
	1.	Nessie validates the request
	2.	Nessie creates a new commit on the active branch
	3.	The commit:
	•	records the new table metadata location
	•	references the new Iceberg snapshot
	4.	Nessie returns success to PyIceberg

At no point does PyIceberg control:
	•	commit summary
	•	commit description
	•	commit authors

Instead, Nessie generates commit messages automatically for Iceberg REST commits.

Real examples you will see in practice:
	•	Update ICEBERG_TABLE ooo.taxi_dataset
	•	delete namespace ooo

These messages are generated by Nessie to describe the catalog-level operation that occurred. They are machine-generated, deterministic, and intentionally minimal.

PyIceberg has no hook to override or customize them.

⸻

7. Why commit messages cannot be set from PyIceberg (today)

Although Nessie supports rich commit metadata:
	•	summary
	•	description
	•	authors

The Iceberg REST API does not require engines to expose these fields.

PyIceberg:
	•	follows the Iceberg REST specification
	•	does not add Nessie-specific extensions
	•	does not expose commit-message hooks

Therefore:

Commit messages created by PyIceberg are implementation-defined and not user-controlled.

This is a limitation of the engine integration, not of Nessie itself.

⸻

8. Auto-generated vs human-authored commit messages

It is important to distinguish two categories of commits:

Auto-generated commits (from PyIceberg)

When PyIceberg performs table operations through the Iceberg REST API:
	•	Nessie creates a commit automatically
	•	the commit message is generated by Nessie
	•	the message reflects the catalog operation, not business intent

Typical messages:
	•	Update ICEBERG_TABLE <namespace>.<table>
	•	delete namespace <namespace>

These commits are technical commits, not narrative ones.

⸻

9. Where human-authored commit messages DO belong

Commit messages are fully supported when:
	•	using the Nessie CLI / REPL
	•	using Nessie’s native REST API
	•	performing catalog-level operations (merge, assign, tag, etc.)

This is why Nessie documentation emphasizes commit messages in CLI examples.

⸻

9. Practical consequence (important)

When using PyIceberg + Nessie REST:
	•	data changes → done by PyIceberg
	•	commit semantics → owned by Nessie
	•	commit narration → handled at the catalog layer

The correct mental model is:

PyIceberg writes data.
Nessie versions catalog state.
Humans add meaning via branches and tags.

⸻

10. Recommended workflow (aligned with design)
	1.	Use PyIceberg for:
	•	appends
	•	overwrites
	•	schema changes
	2.	Use Nessie CLI / REPL for:
	•	branch management
	•	tagging meaningful states
	•	adding commit messages when catalog actions matter
	3.	Treat Nessie commits as:
	•	the authoritative history
	•	the unit of reproducibility

⸻

Final takeaway

PyIceberg does not create “Nessie commits” intentionally; it submits metadata updates. Nessie turns those updates into commits.

Understanding this separation avoids false expectations and leads to clean, robust workflows.
