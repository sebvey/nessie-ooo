Les bases · 01

Un dossier de fichiers Parquet n'est pas une table

Le point de départ

Les données vivent en fichiers Parquet / ORC dans un object store (S3, MinIO…). Pratique et pas cher — mais ça reste un tas de fichiers.

Ce qui manque

  • Pas de transactions : écritures concurrentes = lectures incohérentes.
  • Pas de schema evolution sûre.
  • Lister le bucket pour planifier une query : lent & coûteux.
  • Aucun historique, aucun rollback.

La réponse : Iceberg

Un table format : une spec + une couche de metadata au-dessus des fichiers. Elle décrit exactement quels fichiers composent la table, à chaque instant.

Iceberg n'est ni un moteur ni un stockage. C'est le contrat entre les deux : quels fichiers = la table, maintenant.

Les bases · 02

Ce que ça débloque

ACID transactions

Chaque write est atomique : la table passe d'un état cohérent à un autre — ou rien.

Schema evolution

Add / drop / rename / reorder de colonnes sans réécrire les données ni casser les anciennes lectures.

Hidden partitioning

Le partitionnement est géré par la table, pas par l'utilisateur — et peut évoluer (partition evolution).

Time travel & rollback

Lire la table telle qu'elle était (snapshot passé) ; revenir en arrière en une opération.

Performance

Pruning via les stats (min/max, partitions) : le moteur saute les fichiers inutiles sans les ouvrir.

Open · engine-agnostic

Une spec ouverte lue/écrite par Spark, Trino, Flink, DuckDB, PyIceberg… pas de lock-in.

Les bases · 03

Le modèle mental : catalog → metadata → data

Catalog

L'annuaire : « la table X, c'est ce metadata.json ». Il détient le pointeur vers l'état courant. (Nessie, Glue, REST, Hive…)

Metadata

La couche Iceberg : schéma, partitions, snapshots, et la liste exacte des fichiers de chaque état.

Data

Les vrais fichiers Parquet / ORC dans l'object store. Immutables : on n'édite jamais un fichier, on en écrit de nouveaux.

Écrire = ajouter des data files + de nouvelles metadata, puis faire avancer le pointeur du catalog. Bascule atomique d'un état à l'autre.

En détail · 05

Chaque commit crée un snapshot

Snapshot

Une vue point-in-time (id, timestamp, manifest list) de l'ensemble des fichiers de la table.

Commit

Une opération (append, overwrite, compaction, schema change) qui produit un nouveau metadata.json + un nouveau snapshot.

Le pointeur

current-snapshot-id = le snapshot actif. Le snapshot log garde l'ordre chronologique.

Rien n'est écrasé : on empile des snapshots. La table « avance » en déplaçant un simple pointeur.

En détail · 06

Time travel & rollback

Time travel

Lire un snapshot passé (par id ou timestamp). Le pointeur courant ne bouge pas — on demande juste au moteur de lire un ancien état. Valable tant qu'il n'est pas expiré (expire_snapshots).

Rollback

Remettre l'état courant sur un snapshot antérieur : nouveau metadata.json dont current-snapshot-id pointe vers l'ancien. Aucun fichier copié — seul le pointeur change.

C'est cette mécanique de pointeurs qu'un catalog versionné comme Nessie pousse plus loin : brancher / merger l'état de plusieurs tables d'un coup.

En détail · 07

Pourquoi c'est rapide : le pruning

Les manifests portent des stats par fichier (min/max, null counts, partition bounds, row count). Au planning, le moteur intersecte les prédicats avec ces stats et saute des fichiers entiers sans les ouvrir.

SELECT * FROM orders WHERE amount > 100
file-01amount 5–40skip
file-02amount 12–88skip
file-03amount 60–150lu ✓
file-04amount 0–30skip
file-05amount 120–400lu ✓

Deux étages

manifest list → on saute des manifests entiers ; puis manifest → on saute des fichiers. Pruning coarse puis fin.

Hidden partitioning

La table calcule la partition (ex. day(ts)). L'utilisateur écrit WHERE ts > … sans connaître le schéma de partition.

Zéro index externe

Tout est dans les metadata. Moins de fichiers lus = moins d'I/O = plus rapide & moins cher.

À retenir

Iceberg : des tables, pas des fichiers.

Un table format ouvert qui apporte ACID, schema evolution, snapshots / time travel et pruning — au-dessus de fichiers immuables dans un object store. Un catalog détient le pointeur ; le versionner (Nessie), c'est le Git des données.

metadata.json = l'état commit → nouveau snapshot le pointeur = l'atomicité open · engine-agnostic
