01 · Pourquoi Nessie

Traiter la donnée comme du code

Le problème

  • La pipeline écrit directement dans les tables de prod.
  • La mauvaise donnée est visible tout de suite.
  • Tester en isolation, revenir en arrière, coordonner plusieurs tables : douloureux.

L'idée

Git, mais pour les données.

Nessie versionne le catalogue (les pointeurs de métadonnées), pas les fichiers. On récupère branch / commit / merge / tag sur des tables Iceberg — sans copier la donnée.

Ce que ça débloque

  • Isolation — transformer & tester sur une branche.
  • Merge atomique — promotion tout-ou-rien.
  • Rollback — revenir à un commit précédent.
  • Reproductibilité — auditer via un tag.

Brancher → tester → ne merger que si c'est vert. La mauvaise donnée n'atteint jamais main.

04 · Travailler sur une branche · le principe

La branche, c'est une adresse

1 · L'ADRESSE

Nessie sert un catalogue Iceberg REST par branche : /iceberg/<branche>. Le client ne sait même pas qu'il est sur une branche.

2 · UN SEUL MOTEUR

DuckDB attache l'adresse de la branche, puis lit, calcule, teste et écrit en SQL.

ATTACH 'warehouse' AS lake (TYPE iceberg, ENDPOINT '…/iceberg/pipeline-143205');
3 · MAIN INTOUCHÉ

Personne n'utilise /iceberg/main avant le merge : main ne peut pas bouger. Le merge final est une opération Nessie.

C'est la cible. Avec DuckDB ≤ 1.5.6, l'ATTACH sur une branche échoue : slide suivante.

05 · Travailler sur une branche · aujourd'hui

Le détour par PyIceberg

LE BUG

Nessie répond prefix = <branche> et uri = /iceberg/. DuckDB ignore uri et colle le préfixe derrière l'adresse de la branche :

/iceberg/br/v1/br/… → 404 /iceberg/v1/br/… → 200
LE DÉTOUR

Lecture : le plugin iceberg de dbt-duckdb charge raw.orders via PyIceberg, en Arrow. Écriture : notre plugin iceberg_write réécrit daily_orders sur la branche via PyIceberg.

LE PRIX

Les données transitent en mémoire (Arrow), un plugin maison à maintenir, et le mart est réécrit en entier à chaque run.

Corrigé dans l'extension DuckDB (#1230, juillet 2026), pas encore dans une version publiée. Dès sa sortie : retirer les plugins et revenir au principe de la slide précédente.

06 · Le scénario de démo

Trois actes

Acte 1 — le run qui marche
$ mise run pipeline-ok

Branche → ingestion → dbt build vert → merge dans main + tag.

✓ main est mis à jour, promotion taguée
Acte 2 — le run qui casse · le moment fort
$ mise run pipeline-ko

Mauvaise donnée (montant négatif, client null) → tests rouges → pas de merge, alerte, branche conservée.

⛔ main est resté propre
Acte 3 — explorer & prouver
$ mise run branches
$ mise run notebook

Basculer main ↔ branche -bad dans le notebook · rejouer avec mise run dbt-inspect.

# préparation : mise run stack-reset && mise run stack-up → ardoise vierge, main sans aucune table

07 · Maturité

Qui gère vraiment les branches Nessie ?

Maturité de l'intégration Nessie — surtout écrire/lire sur une branche ≠ main — pas du support Iceberg en général.

Spark—
✓ Mature · natif
Extensions SQL Nessie : CREATE / MERGE BRANCH en SQL. La voie canonique. Contrepartie : JVM, lourd.
PyIcebergingestion + marts
✓ Mature
Branche dans l'URI (/iceberg/<branche>), respecte overrides.uri → n'importe quelle branche, en lecture et écriture.
DuckDBtransformations
⚠ Pas encore
Jusqu'à la 1.5.6 (sept. 2026) : main uniquement, le client ignore overrides.uri (#1145). Corrigé dans l'extension (#1230), pas encore publié. CREATE OR REPLACE toujours absent (#784). On a rusé : DuckDB calcule, PyIceberg écrit sur la branche.
Trino—
⚠ Pas mature
Branche Nessie = propriété statique du catalogue (iceberg.nessie-catalog.ref), ni par session ni par requête (#24134, refusée). Le CREATE BRANCH … IN TABLE de 2025 crée une branche Iceberg sur une table, pas une branche Nessie multi-tables.

Pour un workflow multi-branches dynamique, seuls Spark (natif, lourd) et PyIceberg (léger, via l'URI) sont prêts. D'où notre choix : PyIceberg pour les branches + DuckDB pour le calcul.

08 · Aller plus loin

À creuser

Protéger main
Seul le compte de l'orchestrateur écrit sur main : authentification + règles d'autorisation Nessie par rôle.
Limite : un merge et un commit direct demandent la même permission. On protège par l'identité, pas par le type d'opération.
Maintenance Iceberg à creuser
Compacter les petits fichiers, purger ce qui n'est plus référencé. Mais pas en direct sur les fichiers (expire_snapshots, remove_orphan_files) : on passe par Nessie GC (garbage collector), un programme à part, planifié, qui lit l'API Nessie et supprime les fichiers orphelins.
Le metadata.json écrit par Nessie ne contient que le snapshot courant : l'historique est dans les commits Nessie, sur toutes les branches et tous les tags. Seul Nessie sait ce qui sert encore.

Nessie GC : mark (parcourt toutes les références, collecte le contenu vivant) puis sweep (supprime, table par table, les fichiers que plus rien ne référence).
