# Tickets

The ticket loop: how a ticket goes from an idea to done, whatever stores the tickets. Where tickets live and how each operation is done (filing, changing status, ticking a criterion, closing), the ticket reference and how it shows in branch names and pull requests: the backend file the project imports in its `CLAUDE.md`. Statuses and the ticket template: [`processes/tickets.md`](../processes/tickets.md), in the layer's folder.

- **Entry point**: a new idea, follow-up or problem found along the way becomes a ticket in Backlog, never a widening of the ticket in progress. The agent proposes it (a title and a few lines of why) and files it only once the developer agrees; a request from the developer to file one is that agreement.
  - In a discussion with the developer (refining, a question): propose it in the conversation, when it comes up.
  - While implementing on its own: note it at once in the current ticket's Notes (`Follow-up to propose: …`), and propose it in the finishing report, after the criteria.
- **Refining** a backlog ticket (scope, acceptance criteria) is a discussion: propose, and only set it to Ready once the user agrees.
- **What to work on**: only a Ready ticket, unless the user asks otherwise.
- **Starting**: check the working tree is clean, switch to an up-to-date `main` if needed, create the ticket's branch (named as the backend says), and open its pull request at once, as a draft linked to the ticket (as the backend says). The link sets the ticket to In Progress: no manual move.
- **Working**: tick each acceptance criterion in the ticket as soon as it is met and verified, with how in a few words (`- [x] … (pipeline run, 2026-10-16)`); details go in the Outcome. Untick it if a later change breaks it. A criterion met only in part stays unticked, with what's missing.
- **Finishing**: check every acceptance criterion again (all ticked, or the gap stated), when the work renamed or moved something, grep for every form of the old name, the full one and the short ones (an image `pgsty/mc` is also `mc`; a service is also its container and its volume), in the docs, the ADR index and the tickets; fill the Outcome, set the ticket's `proposed` ADRs to `accepted`, push, mark the pull request ready for review, report the criteria one by one in the message (criterion, state, how verified, what wasn't), and **wait for the user's validation**. The merge is the validation, and it is the developer's action: the developer merges, or asks the agent to; the agent never offers to merge (no question, no suggestion in the report). The pull request is squash-merged into `main`, and the ticket closes as done at the merge.
- **Analysis tickets** (the process's `Type: analysis`): the same loop, without touching the repository. Starting: no branch and no pull request; the ticket goes to In Progress as the backend says. Working: scratch files stay outside the working tree, and anything created to investigate (a branch in a data store, a test table) is removed at the end and listed in the analysis report. Finishing: post the analysis report and fill the Outcome with its proposed tickets (as the backend says), give the finishing report in the message as for any ticket, and **wait for the user's validation**. At the validation the developer decides each proposed ticket: the agent files the ones agreed in Backlog and notes every decision in the Outcome. The ticket closes as done, as the backend says, once every proposal has its decision noted. The process gives the Outcome's form.
- **Never delete a ticket**: an abandoned one is closed with an Outcome saying why.
- **Small work without a ticket** (a fix, an ADR amendment, a few lines asked for directly): on a branch `X666-<object>` (`X666-amend-a001`: the ticket-like ID says there is no ticket), committed there, delivered by a pull request like a ticket's (with no ticket to link), reported, and merged only after the developer's explicit validation. Nothing is committed directly on `main`, and the protection of `main` refuses a direct push.
- **Commit only your own files**: stage the paths you created or changed, never a whole folder that may hold the developer's untracked files.
- **References**: name tickets by their reference in tickets, commits, branches, docs and ADRs. **Never in code or config** (comments, task descriptions, console output): tickets live outside the code (a folder ignored by git, a ticket tool), so a reader of the code can't follow a ticket reference. Write the reason itself instead ("dbt-core 1.11.12 rejects sqlparse 0.6", not "see" a ticket); a link to an upstream issue is fine.
